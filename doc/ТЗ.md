ТЕХНИЧЕСКОЕ ЗАДАНИЕ (ТЗ)
Заказчик: Департамент информационной безопасности «CyberShield Solutions»
Проект: Высокопроизводительный локальный демон (сервер) для мониторинга безопасности и ИИ-анализа системных логов в среде Windows.
1. Бизнес-цель проекта
Создать легковесную, изолированную от интернета (Air-Gapped) систему, которая способна принимать текстовые логи от различных критически важных приложений в реальном времени, анализировать их с помощью встроенной нейросети и мгновенно выявлять подозрительную активность (DDoS-атаки, SQL-инъекции, попытки подбора паролей), не нагружая центральный процессор графическим интерфейсом.

2. Архитектура и технические требования
Модуль 1: Клиентский симулятор (Log Generator)

Тип: Консольное приложение Windows (.exe).
Задача: Имитация работы веб-сервера. Должен генерировать случайные строки логов (как легитимные запросы, так и хакерские атаки) и с высокой скоростью отправлять их на сервер.
Механизм связи (IPC): Использование разделяемой памяти Windows (Memory-Mapped Files) через функции CreateFileMapping и MapViewOfFile.
Синхронизация: Использование именованных Мьютексов (CreateMutex) и Событий (CreateEvent) для предотвращения состояния гонки (Race Condition) при записи данных в общий буфер.
Модуль 2: Серверный движок (Analytics Server)

Тип: Консольное приложение Windows (.exe), работающее в фоновом режиме.
Многопоточность (Multithreading):
Поток А (Приемник): Непрерывно читает IPC-буфер разделяемой памяти, извлекает логи и складывает их в потокобезопасную очередь (std::queue под защитой std::mutex и std::condition_variable).
Пул потоков (Worker Threads): Несколько рабочих потоков параллельно забирают логи из очереди, переводят текст в числовые векторы и отправляют их в модуль ИИ.

Управление ресурсами: Все хэндлы Windows (HANDLE) должны управляться строго в соответствии с концепцией RAII (освобождаться через CloseHandle в деструкторах оберток).
Модуль 3: Модуль ИИ (Собственный ML-движок)

Жесткое ограничение: Запрещено использование сторонних ML-библиотек (TensorFlow, PyTorch, OpenCV и т.д.). Только чистый C++ (STL допускается).
Архитектура сети: Полносвязный многослойный перцептрон (MLP). Минимум один скрытый слой.
Функционал:
Реализация собственного класса Матрицы и математических операций над ними (умножение, транспонирование).
Реализация алгоритма обратного распространения ошибки (Backpropagation) и градиентного спуска для обучения сети.
Функция сохранения обученных весов в бинарный файл (.bin или .dat) и их быстрой загрузки при старте сервера.
Входной слой принимает векторизованную строку (например, через Bag-of-Words или Hashing Trick), выходной слой выдает double от 0.0 до 1.0 (вероятность угрозы).


3. Требования к интерфейсу и выводу (Консоль)
Сервер должен раз в секунду обновлять экран консоли и выводить структурированный дашборд:

Количество обработанных логов в секунду (RPS).
Текущий размер очереди задач в памяти.
Статистику обнаруженных угроз (всего / за последнюю минуту).
При обнаружении критической угрозы (вероятность > 0.85) — выводить в консоль яркое предупреждение с текстом вредоносного лога.

4. Критерии приемки проекта (Что будет оценивать заказчик/тимлид)

Чистота кода: Отсутствие утечек памяти (проверяется через диагностику Visual Studio или контейнеры RAII). Разделение кода на логические модули/библиотеки.
Корректность IPC: Клиент и сервер не должны блокировать друг друга намертво (исключить Deadlocks).
Эффективность ИИ: Самописная нейросеть после обучения на тестовом наборе данных должна показывать точность классификации (Accuracy) не менее 80%.
